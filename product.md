# AnstelleTV — product and build context

<!-- impeccable:product-schema 1 -->

AnstelleTV turns a Jellyfin library into 24/7 retro cable TV on Android phones, tablets, Android TV / Google TV and Fire TV (one APK, touch and D-pad). Channels play programs back to back. There is no backend. All data lives in on-device SQLite (Room). The app also serves a LAN web UI (SvelteKit) where the owner and admins manage the TV from a browser.

The app is native: Kotlin + Jetpack Compose (Compose for TV on TV, Material 3 on phones), with ExoPlayer for playback. There is no WebView. The web UI is for browsers on other devices on the LAN.

## Platform

android

This one record covers both surfaces: the native Android app (phones, tablets, TV) and the SvelteKit web UI it serves on the LAN.

## Users

- **Now:** the owner and their household, watching their own Jellyfin library.
- **Later:** a public release for Jellyfin owners in general. Design for someone who installs the app without help, even though no one outside the household uses it yet.
- **The job:** put the library on like cable TV. Turn it on, surf, land on something, and stop choosing what to watch. On demand is there when they do want to choose.

## Product Purpose

AnstelleTV makes a personal media library feel like broadcast TV again: always-on channels with a schedule, a guide and channel surfing, built from what the library already holds. Success means a new user gets working channels after signing in, with no setup.

## Positioning

- **No server to run.** Everything runs on the TV or phone. Tunarr and ErsatzTV need a separate server plus an IPTV client.
- **Channels build themselves** from the library's own metadata (genres, tags, decades, studios), with no templates or hand curation. Edits are optional and always win.
- **Plays like real TV:** a wall-clock schedule, surfing with the remote, a real guide grid. Seeking in a channel's program moves that channel's schedule with it, so the guide always shows what is on screen.
- **No monetization:** no ads, subscriptions or paid features, unlike QuasiTV and NostalgiaTV.

## Operating Context

- **TV:** Android TV, Google TV and Fire TV, used from the couch with a D-pad remote and no touch. Fire TV has no Google services, so nothing can depend on them (fonts are bundled, not downloaded).
- **Phone and tablet:** the same APK with touch: swipe to surf, tap for controls.
- **Browser on the LAN:** a laptop or phone opens the web UI the app serves. It pairs with a 6-digit PIN the TV shows while the owner's or an admin's profile is on, then manages the TV's servers, channels, themes and backups (see *Web admin*).
- **Jellyfin:** one or more servers, on the LAN or remote, signed in with Quick Connect or a password. Jellyfin UX follows the official Jellyfin apps where one exists.
- **Profiles:** several per device, each a Jellyfin user, with roles (owner, admins, members), PINs and maturity ratings. Channels are shared by every profile (see *Profiles, roles and parental controls*).

3. **Everything on the device.** No backend, no account, nothing beyond Jellyfin and the LAN.

## Decisions and gotchas (learned in Phase 1)

### Android asset packaging

- **No `_`-prefixed asset folders.** AAPT's default ignore pattern drops directories that start with `_`, so SvelteKit's `appDir` is set to `app` instead of `_app`.
- **No `.gz` assets.** The asset packager unpacks `.gz` files and drops the extension. Pre-gzipped web files therefore use the `.gzip` suffix and are listed in `noCompress`. `asset-index.txt` lists every served path, so the server never walks the APK.

### SvelteKit 3

- Configuration moves from `svelte.config.js` (now unsupported) into `sveltekit({...})` in `vite.config.ts`.
- `$lib` is replaced by `#lib` (package.json `imports`), and imports use explicit extensions (`#lib/api.ts`).
- `tsconfig.json` extends `$app/tsconfig` and must include `$app/types`.

### Web server security

- The server binds only to LAN IPv4 addresses and loopback, and rebinds on network changes.
- A remote-address guard allows only RFC 1918, link-local, ULA and loopback addresses.
- Pairing:
  - The TV shows a 6-digit PIN. It lives 2 minutes and allows 5 attempts.
  - At most 10 pairing starts are allowed per 10 minutes. Wrong PINs count across pairings: after 10 within an hour, pairing waits until the hour has passed, so guessing stays slow while nobody watches the TV.
  - The open pairing routes read at most 4 KB of body; anything larger is refused before it is read.
  - On success the browser gets a 256-bit token as an HttpOnly, SameSite=Strict cookie. `Authorization: Bearer` is also accepted.
  - Only the token's SHA-256 is stored. Every request looks it up again (a unique index), so a pairing deleted outside web control — a profile made a member, a restore — stops counting at once.
- Cross-origin writes and cross-origin `/ws` are rejected. Unpaired `/ws` gets a 401 before the upgrade.
- Another AnstelleTV pairs the same way to copy this one's backup (`GET /api/backup/export`, see *Backup and LAN transfer*), so the PIN guards the backup too.
- **A pairing belongs to a profile** (user decision: only the owner and admins use the web UI). The TV approves a pairing only while the owner's or an admin's profile is active (`PairingGate.approver`): on a member's profile `/api/pair/start` answers 403 `no_manager`, and neither the overlay nor the notification shows a PIN. The token is stored with the profile that approved it (`paired_client.profileId`, deleted with the profile), and it counts only while that profile is the owner or an admin, checked in memory on every request; making the profile a member deletes its pairings, so making it an admin again doesn't bring them back. Restore (`POST /api/backup/restore`) is the owner's alone, as in the app.
- An open `/ws` checks its pairing again whenever paired browsers or profiles change, and closes with 1008 once it no longer counts; the web UI then goes back to pairing.

### Platform

- **Tokens:** `EncryptedSharedPreferences` is deprecated, so Jellyfin tokens are encrypted with an Android Keystore AES-256-GCM key and only the ciphertext sits in the private `jellyfin_tokens` prefs file (`KeystoreTokenStore`). A Keystore or decrypt failure drops the token and the server shows "Signed out", instead of crashing.
- **Android 17 (API 37):** `ACCESS_LOCAL_NETWORK` is declared and requested at runtime.
- **Foreground service:** the web server runs as a `specialUse` foreground service.
- **FFmpeg decoder:** `org.jellyfin.media3:media3-ffmpeg-decoder` latest is `1.9.0+1`, built for Media3 1.9. It works with Media3 1.11.1: `FfmpegDecoderTest` decodes AC3, E-AC3, DTS and TrueHD on a device. If a later Media3 breaks that test, pin Media3 to the extension's version.
- **Database migrations:** debug builds fall back to destructive migration while the schema moves between phases. Pre-release schema versions (listed in `AnstelleDatabase.PRE_RELEASE_VERSIONS`) are also dropped in release builds. Real migrations start with the first public release.
- **Cleartext HTTP** is allowed app-wide, because LAN Jellyfin, HDHomeRun and M3U sources use plain HTTP on arbitrary IPs.
- **Gradle warning:** builds print `Configuration.setVisible` deprecation warnings that come from third-party Gradle plugins. They are harmless until Gradle 11.

### Jellyfin (learned in Phase 2)

- **Adding a server works like the official Jellyfin apps.** There is one "Server address" field that takes an IP address, a host name or a full URL. The SDK's `discovery.getAddressCandidates()` expands the input (with and without HTTPS, ports 8096/8920), and `getRecommendedServers()` checks every candidate; the best-scoring one wins. There is no separate home/remote address (user decision). Adding the same server again under another address updates the existing entry, matched by server Id, so its libraries stay.
- **Sign-in:** Quick Connect (the code is polled every 3 s) or username and password. Signing in as a different user on a known server triggers a full re-fetch.
- **Removing a server** (user decision): the TV and web UI delete its linked accounts and synced content. A linked profile is deleted with its personal settings, history and pairings unless it has a valid account on another signed-in server. If the owner would be deleted while another signed-in server remains, the owner must choose a signed-in admin who will survive the removal; ownership transfer and deletion commit together. Without an eligible admin, removal waits until one is signed in on another server. Expired and signed-out servers and profiles do not count: remaining stored sessions are checked with Jellyfin before showing removal choices and checked again before deleting; an unreachable session is retained unless Jellyfin rejects it. When no signed-in server or valid profile would remain, only the owner can confirm starting over: all servers (including stale entries), profiles, history, channels, custom themes, settings and credentials are cleared, web control stops, and the app immediately returns to first-server setup. Built-in themes stay installed.
- **SDK dates are device-local.** The SDK decodes server timestamps into `LocalDateTime` in the device's zone, and sends `LocalDateTime` query parameters with the device's UTC offset. The server handles offset-qualified `minDateLastSaved` correctly; a zone-less value is read differently. Convert only through `SdkTime.kt`. Unit tests run in `Asia/Manila` so UTC/local mix-ups fail on any machine.
- **Grouped views:** a user view that groups libraries (one "TV Shows" view over several TV libraries) is not a library. Real libraries come from `CollectionFolder` views plus `/UserViews/GroupingOptions`, with the collection type from `/Items/{id}`.
- **Incremental sync:** `BaseItemDto` has no `DateLastSaved`, so each library's watermark is the *server* clock (`/GetUtcTime`) at the start of its last sync, re-read with a 5-minute overlap.
- **Series first:** episodes usually have no genres, studios, tags or rating of their own. Series are stored first and episodes inherit from them at sync time; a changed series re-reads its episodes.
- **Reconciliation:** deletions don't touch `DateLastSaved`. An ID-only listing runs at least every 6 hours and on manual sync. It deletes vanished items and sets `inputsHash = 0` on the schedules that air them, so the scheduler regenerates those channels.
- **Fields:** `MediaSources` (source id, container, streams) cost about 8 KB per item, so pages hold 150 items.
- **Artwork:** item pages ask for one image of each kind: the poster (`Primary`), the first backdrop and the title logo. Their tags are stored (`primaryImageTag`, `backdropImageTag`, `logoImageTag`) and the URLs are built locally with the tag (`Artwork`, `jellyfinImageUrl`), so no page asks the server whether art exists. Episodes rarely have a backdrop or logo of their own; they use their series'.
- **Ratings:** `/Localization/ParentalRatings` only lists the server's metadata country, while real items carry "12", "NC16", "M18", "PG13" or "6+". `RatingScores` falls back to a punctuation-insensitive match, then to the age written in the rating.
- **Libraries:** movies, series, music videos, home videos and mixed libraries are synced. Music, books, photos, playlists and live TV are listed but not synced (music is on hold). Jellyfin's Collections view only gathers items the libraries already hold, so it isn't listed as a library. Each library can be turned on or off on the server screen. The choice takes effect at the next sync, never at once and with no sync of its own: the sync deletes a library's items once it is off, and fetches it in full once it is back on.
- **Logging:** the SDK logs through kotlin-logging. On Android that maps to logcat; JVM unit tests need `slf4j-nop` on the test runtime classpath.

### Scheduler (learned in Phase 3)

- **Back to back.** Each program airs for exactly its own length and the next one starts the moment it ends, so guide times land on odd minutes (8:00, 8:24, 8:46). One `schedule_slot` row is one whole airing. The first program of a new schedule starts at the time the caller passes in.
- **Staggered starts** (user decision). Channels must not all start together, so `ScheduleEngine.staggered` moves a fresh state back until now falls at a random point of its first program, as if the channel had been on air for a while. The point is a fraction of that program's own length (a 22-minute episode or a 2-hour movie alike), taken from the state's generator without advancing it, so the same state always gives the same start. It costs one extra engine step per channel and stores nothing. Off air starts at now. When a daypart or season edge falls inside the lead, a different first program may air; the start is still staggered.
- **Pure and deterministic.** `ScheduleEngine.generate(inputs, state, until)` has no clock, I/O or shared state. Candidates are sorted canonically (show, season, episode, id) by `CandidatePool`, so load order never changes a schedule. Specials (season 0) sort after the regular seasons; items without numbers sort last.
- **Resumable state.** `EngineState` holds the next start time, the SplitMix64 state, a per-series "next episode at or after (season, episode, id)" cursor, the movies' release-order cursor, shuffle decks, the running block, the last program's item and when each movie inside the movie gap last started. A shuffle deck is stored as its seed, position and held movies, not its order, so the blob costs about 50 bytes per played series and per deck. Cursors are positions, not indexes, so new or deleted episodes don't reset a series. Extending 10 days by 20 equals generating 30 at once (tested for every pairing of series and movie playback, with and without the movie gap, with seasons and dayparts, through `encode`/`decode`). A seek moves the stored movie starts with the schedule (`EngineState.shifted`).
- **Regeneration.** `ScheduleInputs.fingerprint()` is the `inputsHash` (never 0, since 0 marks a schedule stale), including a scheduling-policy marker so existing schedules adopt the completed-series rotation rule. After a change, `ScheduleEngine.rewind` moves each series back to its first discarded episode and the movies to the first discarded movie. When the history includes a kept episode of that series, it resumes after the last kept episode instead, preserving completion when the discarded episode belongs to a future rerun. It takes the programs kept in the day before the cut (`ScheduleDao.programsBetween`), so the repeat rules go on across it, and the shuffle decks start over from them.
- **Series and movies play apart** (user decision). Each program is an episode or a movie (any item outside a series, music videos too): a show is picked by weight (a series' weight is the highest of its episodes'; a movie is a show of its own), and that says which kind airs. Each kind then follows its own playback (`ChannelConfig.series`, `.movies`), with the same three choices: SHUFFLE deals every eligible episode, or movie, once per deck (weights don't apply inside it); EPISODE_ORDER plays the picked series' next episode, or the next movie by release date (premiere date, else January 1 of its year, else last); BLOCKS plays 2–4 of those in a row. At first setup, ordered series present in the base or seasonal lineups open at seeded random regular episodes, with those opening positions stored in their cursors; specials and unnumbered episodes open a series only when it has nothing else. Later schedule extensions continue the saved positions. Series added later and reruns start at the first episode. A completed series sits out while any other eligible series has episodes remaining; when all eligible series finish, another rotation begins, still selected by weight. Blocks end at the final eligible episode rather than wrapping into a rerun. Eligibility follows the current season and daypart, so unavailable series never prevent a rerun or leave a playable channel off air. Movies still open at a movie picked from the seed and wrap in release order; shuffle still deals every eligible item once per deck. The stored engine-state format is unchanged.
- **Repeats** (user decision: the same movie twice in a row is never allowed). Nothing airs right after itself, and with a movie gap (`movieGapMs`, 24 hours for *Once daily*) a movie doesn't start again within the gap of its last start, while anything else on the lineup can air instead: a movie turn with nothing allowed becomes a series turn, and a shuffle deck holds back recently aired movies until its own airtime has waited them out (`DeckHold`). Only when nothing else can air do the rules give way, the gap first, then the repeat: a lone movie still airs, back to back.
- **Seasons and dayparts** are evaluated at each program's local start. Month/day ranges may wrap the year. A daypart window may wrap midnight; unrated items never pass its rating limits (same as the SQL kid filter). Shuffle keeps a separate deck per lineup, daypart and kind. `SeasonMode.VISIBLE_IN_RANGE` is only about channel visibility, so it is not an engine input.
- **Off air.** When nothing is eligible (e.g. no item passes a kids daypart), the channel gets an `OFF_AIR` row until the next daypart edge or local midnight, whichever comes first, and the TV shows an off-air screen. A channel with an empty pool is off air one local day at a time.
- **`nowPlaying`** uses the same rule as the SQL lookup: the last slot starting at or before now, if now is before its end. The media position is the time since the slot started. `ScheduleRepository` answers it with one indexed query and stores generated slots and state in one transaction.

### Channels (learned in Phase 4)

- **Rules.** A lineup is rule groups (OR) of rules (AND), plus series or movies always included (with a weight) and never included. Text compares ignoring case. `KEYWORD` matches whole words or phrases in the title, the show title and the tags (punctuation ignored), not overviews, which matched too loosely. `OFFICIAL_RATING` with `AT_MOST`/`AT_LEAST`/`BETWEEN` compares the numeric score; unrated items never pass a limit. `DECADE` values are first years (1980). `KIND` compares a show's kind (anime, cartoons, `unclear` or `none`; see *Library channels*). A program's running time only sets the length of its airing; there is no rule on it. A missing value only passes `NOT_ANY_OF`. An item's weight is the highest of the groups and picks that take it; excludes always win.
- **Storage.** Lineups are `channel_rule` rows: each group's rules share a `logicGroup` and carry the group's weight; picks are `INCLUDE`/`EXCLUDE` rows with `logicGroup` -1; lists are `|`-separated. A daypart that names a `ruleLogicGroup` uses that group only as an extra filter inside its window, so the group is left out of the base lineup. Show and item picks store Jellyfin ids, which survive a resync.
- **Matching is in memory.** `MediaItemDao.catalog()` loads every item once with the fields rules test; `LineupMatcher` compiles the rules (lowercased sets, parsed numbers). 50,000 items match in under 50 ms on the JVM (unit-tested).
- **Schedules follow the channel.** `ScheduleUpdater` keeps every visible channel 8 days ahead (user decision: the guide shows 7; it tops up once a schedule is 12 hours short, so the guide's last day is always there); a schedule stored further ahead is cut back to that, keeping the airing on now and the next one. A new channel starts staggered: now falls somewhere inside its first program. When the inputs hash changes (rules, series or movie playback, Once daily, matched items, the device zone) or sync marks the schedule stale, the airing on now and the next one stay and the rest is regenerated; an off-air stretch or an airing whose item was deleted is not kept. A schedule that ran out while the app was unused restarts staggered the same way, never before its last airing, instead of filling the past. A slot running across the point a schedule is replaced from ends there. Hidden channels are not scheduled. Edits in the channel screens reschedule that channel right away.
- **Channel numbers** are 0–9999, unique and never typed in (user decision): every channel is in a group, and its number is its place A to Z in that group, counted from the group's start (`ChannelNumbering`, unit-tested). Names compare with case and accents ignored and numbers by value ("90s TV" before "2010s TV"). Groups are numbered from the lowest start up, skipping numbers a lower one gave out, so numbers stay unique even when starts overlap. Creating, renaming, deleting or moving a channel, a sync and changing a start renumber every channel at once. The player's route uses -1 for "no channel asked for", since 0 is a real number.
- **Logos** are made standard once, when stored in `files/logos` (`ChannelLogos`), the way set-top picons are: decoded no larger than about 1600 px a side, their transparent margins trimmed (`LogoMargins`, unit-tested; an opaque logo stays whole, since its colored plate is part of it), fitted inside a 5:3 box of 400 × 240 px and never enlarged, then saved lossless: WebP on Android 10 and later (`WEBP_LOSSLESS` from 11, `WEBP` at 100 on 10), PNG before, where WebP can only be lossy. Each file gets a new name per upload (`<channel>-<time>.s1.webp`) so cached copies refresh; logos stored before the standard are made again once by `ChannelRepository.standardizeLogos`, which `ScheduleWorker` runs at app start (a 1200 × 1200 PNG of 13 KB with wide margins became a 6.9 KB WebP). Everywhere a logo shows, it is fitted into the same 5:3 box (`ChannelLogo` in `core/theme`), loaded with no crossfade; only channels someone built take one (see *Library channels are locked*). Phones pick one with the system picker; any device can upload over the web API (`PUT /api/channels/{id}/logo` with the image bytes, at most 4 MB; `GET` serves it, `DELETE` removes it). `/api/channels` reports a versioned `logoUrl`, and `GET` answers with `image/webp` or `image/png` as the file is.

### Library channels

- **Made from metadata.** `ChannelGenerator` decides which channels exist and what they air from the library's own genres, tags, years and studios (the values Jellyfin's metadata providers fill in, such as TMDB and TVDB). Nothing lists titles, studios or networks. Four segments, each a guide group, in this order:
  - **Productions:** each Studios value by its own name, airing everything it made (series and movies, anime, cartoons and the rest). For series that includes the network ("Netflix", "NBC").
  - **Decades:** TV, movies and each media type's series and movies by decade ("90s TV", "80s Movies", "2010s Anime", "2010s Anime Movies"). An episode counts in the decade it aired.
  - **Genres:** each genre, each pair of genres and each genre with a media type, as a series channel and a movie channel ("Fright Night" and "Horror Picture Show" for Horror, "Case Files" and "Crime Sagas" for Crime and Drama, "Anime After Dark" and "Anime Midnight Show" for Anime and Horror).
  - **Themes:** each tag ("Isekai"), airing everything with it.
- **What may mix.** A genre or decade channel airs series or movies, never both, and one kind of show: anime, cartoons, or neither. Themes and productions air everything with their tag or studio. Channels someone builds may mix anything. The lineup builder doesn't offer kind or decade rules (user decision: genres, tags, keywords and years already say them); stored rules on them still match.
- **Anime or cartoon** is decided per show by `MediaKinds` in the catalog, from the genres, tags and audio languages of all its episodes together. Anime: its genres or tags say anime (TMDB marks anime with the `anime` keyword) and its audio has Japanese, or no audio language is known. Cartoons: its genres say animation, nothing says anime, and no episode or movie plays Japanese first. Animation whose signals disagree (an anime genre with only English audio, an untagged film that plays Japanese, a western cartoon whose file defaults to a Japanese dub) is *unclear* and airs on no genre or decade channel. The word list says which language confirms a type (`"language": "jpn"` for Anime). A library folder's name decides nothing: one can hold both.
- **Order and numbers.** Segments in that order, each a library group (`channel_group.libraryKey`) counting up from its own start: Productions 1000, Decades 2000, Genres 3000, Themes 4000 by default, changed on Settings, Channels, *Groups* (any start from 0 to 9999; changing one renumbers that group at once). Inside a group channels are numbered A to Z (see *Channel numbers*).
- **Genre channel names** come from the word list: `names` for series channels and `movieNames` for movie channels, retro TV-block names of at most three words for every genre TMDB and TVDB use (35, after merging spellings), each of them with Anime and with Cartoons, and every pair of them (700 names each; a unit test checks every combination has both, none of the 1,400 repeats and none is longer than three words). A genre outside that list (a custom one added in Jellyfin) gets a made-up name, with "Movies" after it for a movie channel.
- **Made-up names.** A genre has one modifier everywhere: its adjective when it has one ("Comedic Drama", "Comedic Anime", "Comedic Cartoons"), else itself ("Sports Anime", "Drama Cartoons"). In a pair, a head genre (Drama, Comedy, Thriller, Adventure…) ends the name ("Action Comedy", "Action Adventure", "Crime Drama"); between two heads or two others, the genre with an adjective modifies ("Comedic Drama", "Romantic Comedy"), else the one with fewer shows ("Mystery Thriller"). A genre value with `&` ("Sci-Fi & Fantasy") is two genres, so no name joins genres with "&". All-lowercase tags are title-cased ("Based on Manga"). Decades 1920–1990 are written short ("90s"), others in full ("2010s").
- **Word list.** `core/data/src/main/assets/channel-words.json` holds only language: the media types with the genres, tags and audio language that mark them, spellings of one genre (`Sci-Fi` = `Science Fiction`), head genres, adjectives, tags to ignore (TMDB's credit-stinger, sequel/remake, time-setting and mood keywords such as "amused" or "admiring"), title-case minor words and the genre channel names. It names no title, studio or network and decides no lineup. An unreadable file is logged and channels are made without it.
- **Thresholds** (`ChannelGenerator`): a channel needs 3 shows (a movie counts as one) and 12 hours of airtime; a theme needs 8 shows. A channel of movies alone needs a full day of them at any scale (user decision: it isn't made otherwise), so each movie airs once a day (`OncePerDay`). Tags on more than half the library's shows, tags that equal a genre and media-type tags are skipped. A channel whose shows are 85% the same as a channel kept before it (genres first, then themes, decades and productions) is dropped, and so is a pair or typed genre that is 85% its parent genre or media type. A studio with 90% of its shows inside a bigger kept studio is dropped too: anime lists every regional station that carried a show, and those stations mostly repeat a bigger network's lineup.
- **Lineups** are ordinary rules, so the lineup editor, the matcher and the scheduler treat library channels like any other: every library spelling of the genre, tag or studio (`ANY_OF`), a `KIND` rule (anime, cartoons or `none`) and an exact `MEDIA_TYPE` rule for genre and decade channels, a `DECADE` rule. A unit test checks that every lineup matches exactly the items the generator counted, and that genre and decade channels keep to one kind and one media type. Every library channel plays series in episode order and shuffles its movies once a day.
- **Following the library.** `ScheduleWorker` runs `ChannelRepository.syncGenerated()` after every library sync, and once after an app update or time-zone change, for the whole library: channels are every profile's. Ordinary app starts and twice-daily runs only top up schedules that are due. A full run adds the channels the library newly has content for, updates the name, lineup and group of the rest, removes a library channel that is no longer made unless it would still be made at three quarters of the thresholds (so channels near the limit don't flicker; a channel that stops qualifying for another reason goes at once), and renumbers every channel. `GeneratedChannelSync` makes these decisions and is unit-tested. While a library is still on its first fetch (just turned on, its server just added, or restored from a backup), no library channel is removed: what is missing may only not have arrived yet.
- **Library channels are locked** (user decision): they follow the library and can only be hidden or favorited. Lineup, group, playback, name, logo and deletion belong to channels someone built; the repository refuses them on a library channel (`LibraryChannelLockedException`, a 403 from the logo API).
- **Groups number channels** (user decision: a group and its numbers are one thing). *New group* asks for a name, then the start, which defaults to the next thousand after every start and channel number, the library's four counted before they exist (5000, then 6000, 7000…; `GroupRules`, unit-tested). No two groups share a name or a start, and the library's names and default starts are kept for them. A channel someone builds always goes into a group someone made, picked under its Name (user decision; the library's groups are never offered); New channel and Add to channel start with the one the last channel built went into (`channels.new.group`). The library's groups only move and change their start; a group someone made is renamed, moved, given a new start, and deleted once it is empty.

### Playback (learned in Phase 5)

- **Back out of a player.** The live player always leaves to Live TV. The on-demand player always leaves to the on-demand media page it was playing from (the channel's page, opened in the player's place when it was started from the guide). A media page always leaves to the On Demand main page, never to the page that opened it. The players' own back handling (overlay, panels) still comes first.

- **It plays like TV.** Channels follow the schedule's wall clock. Up/down or the channel keys surf, digits enter a number (it tunes 2 s after the last digit), the banner snaps in on every tune and seek with its keys showing (audio and subtitles on the left, *Restart* on the right), focus left on the picture so surfing and seeking keep working, and OK, Info or Menu moves focus into the keys. Phones swipe up or down to surf (no channel keys), swipe left or right to seek 10 s back or 30 s ahead (on demand too), tap for the banner and tap or drag its ladder to seek. A finger down in the banner (scrolling a track list) holds it up until it lifts. Phones and tablets turn the player sideways and hide the system bars while it is open; going from the live player to the on-demand one stays sideways, and the rest of the app on phones and tablets is locked upright from launch, so leaving a player always turns the screen back to portrait (user decision).
- **Seeking moves the schedule** (user decision). Left and right (or rewind and fast-forward) seek 10 s back and 30 s ahead, like any video, and *Restart* seeks to 0. The airing then starts where the new position puts it, and everything after it on that channel moves by the same amount, engine state included (`ScheduleRepository.shift`, one transaction). Airings it now overlaps are cut short; when it moves later, the part already shown stays in the guide's history as an airing of its own. Seeks stop 3 s short of the program's end and are written in order. Off-air stretches move with the rest, so a daypart edge moves too.
- **Stream facts.** Both players' banners carry a technical line: the server's name first, then DIRECT PLAY or TRANSCODING, then the file's quality ("4K Dolby Vision", "1080p"), video ("HEVC 10-bit") and audio ("TrueHD Atmos 7.1") as outlined badges (`StreamFacts`). They describe the file as synced; a transcoded stream plays the server's H.264 and AAC output.
- **Tuning makes no server call.** `ChannelPlayer` reads the airing from SQLite, decides direct play or HLS locally (`StreamPlanner` against a `CapabilityProbe` snapshot of `MediaCodecList`, `AudioCapabilities` and the FFmpeg extension) and builds the stream URL from the stored server address. The access token never goes into a URL: the player's data source adds the server's `Authorization` header to every media request, HLS segments included.
- **Direct play** streams the file (`/Videos/{id}/stream?static=true`). **HLS** (`/Videos/{id}/master.m3u8`, H.264 + stereo AAC, video and audio copied when they already fit) is used when the container, video codec, size or bit depth doesn't fit; audio almost never forces it, because the FFmpeg extension decodes AC3, E-AC3, DTS and TrueHD. Jellyfin's playlist covers the whole item, so the player simply starts at the airing's position. A file that turns out not to play directly is retried once as HLS. A transcoded stream carries one audio track and no subtitles of its own (see *Audio and subtitles*).
- **Back to back.** Plain-subtitle programs use a playlist with 4 s of next-item preloading, within the player's existing buffer budget. For ASS programs, whose libass state cannot share a playlist, the existing standby prepares the next allowed program from position zero during the current program's final 30 s and swaps in at its end. Within 10 s of the last tune or guide move the standby stays the surfer's, and the boundary waits until they rest. Fonts and the stream are prepared before the boundary; no third player is created. A device with one video decoder buffers on muted audio and acquires video only at hand-off. Shorter or longer real runtimes still move the channel schedule. Restricted or off-air programs are never preloaded. Network starvation and decoder initialization can still cause a delay; hardware and network timings need real-device measurements.
- **Real length.** Jellyfin and the file's own header can both give a 24-minute episode a runtime of 4 to 10 hours, or of a minute. Unique background duration work compares regular episodes within each series and season, requiring at least three episodes (falling back to the series when a season is smaller). A runtime less than half or more than twice the median triggers a file check; surrounding episodes never provide a guessed replacement. `AndroidFileDurationProbe` seeks to the final indexed cluster, reads audio/video sample timestamps through EOF, and includes the last sample's observed span, ignoring the bad header. Each maintenance pass probes one file at a time, outside scheduling and sync locks, with one 20 s total deadline and at most 10,000 samples per file. Failed identities retry after 24 hours; changed sources are eligible immediately. Catalog reads, startup scheduling and missing-schedule tuning apply only saved local corrections and never wait for a remote probe. Measurements are cached by server, item, media-source id and reported runtime, including confirmed legitimate long episodes, so unchanged files are not probed repeatedly. Corrections apply to existing libraries on their next schedule update and survive incoming sync metadata; a changed source or reported runtime invalidates the cache. A current or next airing whose duration is stale is regenerated too, so a broken multi-hour airing is not protected indefinitely. The active player checks its stored airing every 10 s and retunes if that airing was replaced; an unchanged slot is left alone even when its file is still playing past the advertised end. Natural playback ends also correct mismatches: when a program ends more than 5 s off its airing's end, `ScheduleRepository.endAt` moves everything after it, engine state included. A direct file seen playing up to its end also supplies a persistent measurement through `MediaDurations.remember`, and all schedules are updated (`ProgramLength`, unit-tested). `MediaDurationTest` opt-in device checks exercise the normal schedule updater and verify current/future slot lengths and continuity without test SQL repairs.
- **Player pool.** An active ExoPlayer and up to two lazily created standbys. While the viewer surfs, both neighbours are kept ready (user decision): the next and previous channel in the full-screen player, the one in the surfing direction first, and the rows above and below in the guide (`surfNeighbours`, unit-tested). They are warmed as soon as a tune shows its first frame (before the next program is looked up) and re-aimed every 20 s; a standby already on a wanted channel stays. The second standby prepares direct-play programs only: one needing HLS would make the server transcode a channel nobody watches. With one standby waiting in the last surfing direction, a press back, the first press after a rest and a press before the standby was ready all tuned cold, half the presses of a mixed up and down surf on the TV AVD. While it waits paused, each standby follows its program's live position at the keyframe before it (`SeekParameters.PREVIOUS_SYNC` while it is the standby), moving once it falls half the buffer behind; the swap seeks the same way just before the player goes on screen, where seeks are exact again. Every player keeps its buffer from the keyframe before its position (`setBackBuffer(0, true)`), so those seeks land inside the buffer and the first frame needs no decoding up to an exact spot. Without it a paused player drops that keyframe and every seek downloads again (seen as one new load a second while following); with exact follow seeks, the swap's keyframe lay before the kept audio and downloaded again too. A pre-warm starts at the live point itself, so its first follow seek loads once more, away from any switch. The channel can run up to one keyframe interval behind its schedule, which the next program's start catches up when more than 3 s. Resting 10 s on a channel drops back to one standby, the one in the surfing direction (at the next 20 s re-aim, or at once when an ASS boundary needs it), and two minutes after the last tune or guide move that one is let go too (user decision), so a long watch streams, buffers and decodes one channel; the first press after it tunes cold, the ones after it warm again. Tuning to a standby swaps it with the active player, which stops. Keeping that player ready as the neighbour the other way was tried and dropped: it held the active player's whole buffer, 55–90 MB more Java heap on the TV AVD, for the warm switches fresh standbys give too. Standbys stay paused and muted, with audio and subtitle tracks enabled so media continues loading; each buffer is capped at 4 s / 8 MB. Devices with Android?s low-RAM flag, at most 2 GiB physical RAM, or at most 128 MB heap use a 32 MB active target and a 2 s / 4 MB standby. Standby video decoding stays off on these devices and on devices without a second hardware H.264 decoder; elsewhere only the first standby slot decodes video, so no more than two video decoders run. Normal devices retain a 64 MB active target. Current-program preparation precedes upcoming stream/banner resolution; a valid standby is promoted without rebuilding its stream. Font downloads share one cancellable three-second deadline. libass never lets go of a font, so a player whose libass holds more than 48 MB of fonts (16 MB on low-memory devices) is replaced by a new one the next time it is stopped, tuned cold or re-aimed as a standby.
- **Tracks.** Each program starts on the profile's audio and subtitle defaults; picking a track in the player only changes the program on now (see *Audio and subtitles*).
- **Jellyfin watch history** (Settings, *Live TV* and *On demand*, per profile, user decision): Jellyfin keeps one watched mark and one resume point per item for all its apps, so Live TV and On demand each choose what they leave there (`WatchSync`): *Both*, *Status*, *Progress* or *Off*. Live TV defaults to *Status*, so channel airings never move the resume point On demand left; On demand defaults to *Both*, like Jellyfin's own apps. Each is a choice row that opens its four choices as a radio list, each with what it does (the next panel on TV, a dialog on touch).
  - **The setting comes first** (user decision): the active player?s source selects its setting before anything reaches Jellyfin. Live TV ? Watch on Demand stops the Live TV session and uses On Demand settings; carried channel information is navigation context only. *Off* sends nothing; *Status* sends only a watched mark when playback finishes or its ending position reaches 90% (Jellyfin's default). *Progress* updates only resume position and last-played time, never the watched flag or play count. *Both* sends the usual session reports and marks a completed view. Live TV requires at least 30 s of actual playback for any mode, even after joining near the end or when a short program ends; pauses, buffering, seeking and preloading do not count. A direct-play stream that falls back to HLS remains the same view.
  - **Progress** writes the resume position through `/UserItems/{id}/UserData`, every five seconds and immediately on pause, resume, seek and stop in either player. It separately sends metadata-only Now Playing reports: an empty top-level library ID and a generated metadata ID keep normal reports and server timeout cleanup away from the real item?s watched flag and play count. The title and time appear without a library-item link. Its ending position remains progress even beyond the completion threshold. Posters and episode lists trust Jellyfin's explicit played flag and never infer watched from a near-end resume point. *Both* retains normal session reporting. Successful `PlaybackReporter.updates` refresh visible history; hidden catalogs invalidate their cache without reading the library every five seconds. Completed writes and failed attempts use separate flows. Reporting runs off the playback path, coalesces queued positions, preserves lifecycle ordering, retries transient errors with bounded backoff and invalidates only the failed credential on HTTP 401. Same-user authentication resumes pending work; another user?s credential is never substituted.
  - **Completion** follows the ending position or the player reaching its natural end, not how much of the beginning was seen (user decision). A late join finishing after 30 s counts on Live TV; a hop after 29.999 s at 95% sends nothing. On Demand has no 30 s gate for Jellyfin. A natural end counts even when runtime metadata is wrong; Progress saves the player's actual end position, not that metadata's duration. The Live TV gate uses a monotonic `PlayClock`, so device-clock jumps cannot qualify a hop; a separate wall-clock instance splits dashboard time by calendar day.
  - **Marks** (`WatchRules`, unit-tested): *Status* and a completed *Both* view set only the played flag through `/UserItems/{id}/UserData`; Status preserves existing resume data and play count. *Progress* omits the played flag entirely from its resume update, so a completed program cannot be marked watched by the app or by a session stop. Live TV's *Both* mode remembers the prior flag and restores it at start and after an incomplete stop if Jellyfin changed it.
  - Every view is also handed to the profile's dashboard, whatever these settings (see *Dashboard*).
- **FFmpeg extension:** `media3-ffmpeg-decoder` 1.9.0+1 works with Media3 1.11.1; `FfmpegDecoderTest` decodes AC3, E-AC3, DTS and TrueHD samples on a device (`./gradlew :core:player:connectedDebugAndroidTest`).
- **`LoadControl` in Kotlin:** delegating with `by` skips the interface's Java default methods and ExoPlayer then crashes in `getBackBufferDurationUs`; `PoolLoadControl` forwards every method by hand.
- **OK on key-up:** the player screen acts on OK when the key is released. Acting on key-down moves focus to the controls, which then take the key-up as a click.

### Guide and on demand (learned in Phase 6)

- **Guide row heights** (user decision). Compact, Comfortable and Spacious use 48, 56 and 64 dp on both touch and TV, in equal 8 dp steps. The guide and theme previews use this scale. EPG program cells use 2 dp vertical text padding at every density on both platforms.

- **The guide** is a preview window playing the channel on now, the selected program's details over its show's backdrop (the show's logo in place of its title when there is one; the episode with its rating and year on one line; the time, then the file's quality, video and audio as badges, the same ones the player's banner shows; the channel's ident in the top-end corner; three lines kept for the overview on TV, under a 56 dp logo, five on phones), group tabs (all channels, favorites, then each group that has channels; the open tab is remembered per profile) and the program grid. The details follow the selection only while it is on now: a program that aired or is still to come has no picture in the preview, so the details stay on what the preview plays (user decision). It opens at the current half hour and goes 7 days ahead.
- **Grid layout.** A lazy column of channel rows sharing one time state. Each row's cells are a `ProgramStrip`: parallel arrays of starts, ends, item ids and titles, so a row lays out without an object per cell. A row composes only the cells inside the visible hours plus 30 minutes on each side, and a custom layout places them by reading the time state, so scrolling the hours relays rows out without recomposing them. A program that began before the visible hours is clipped to the left edge so its title stays readable. The now line and the dimmed past are drawn over the rows from a clock that ticks twice a minute, without recomposition.
- **Loading.** Cells are read from SQLite per 6-hour window for every channel at once (one query joining `schedule_slot` and `media_item`, range-bounded by the longest slot), kept in an LRU of 8 windows, with the windows on either side fetched ahead. Schedule or library changes clear the cache and the visible windows load again.
- **D-pad.** The grid is one focus target that moves the selection itself: right and left step cell to cell and page the hours when a cell starts within 15 minutes of an edge; up and down keep the time, so the cell airing at that moment is selected; channel or page keys move a screenful. Left at the guide's start and up from the first row hand focus to the drawer and the tabs. Entering the drawer lands on the open destination. The guide keeps its place (hours, selection, scroll) while the player or another page is on top; a new launch opens at the current half hour.
- **Touch.** Drag or fling sideways moves the hours, the list scrolls vertically, tap selects, long-press opens the actions.
- **Selecting and watching** (like TiviMate): OK or a tap on a program airing now shows its channel in the preview window; again, it goes full screen. Holding OK, Menu, or OK on a later program opens its actions under a header that says when it airs (ON NOW with the time left, LATER, or AIRED). The words depend on when it airs (see *Watch choices*): on now, *Watch live*, *Start over* and *Watch on demand*; later or aired, *Watch now*; always *Add show to a channel* or *Add movie to a channel*. The play choices go straight to the on-demand player, which keeps the airing they were picked from (channel and start time) for its *On Demand* key. An off-air stretch on now offers *Watch live* with when it ends; one still to come opens nothing. Back or a tap outside closes the actions, and the D-pad never leaves them for the guide behind. Opened by holding OK, they wait for OK to be released and pressed again before acting. Each preview readies the rows above and below on the standby players, the one in the direction browsing moves first (down when it can't tell), so moving on or back tunes from one.
- **Watch choices** (`WatchChoices`, unit-tested) are one vocabulary for the guide's actions and a channel's page in On demand, each with one line saying what happens, short enough for one row and never repeating the program's name. *Watch live* and *Start over* stay on the channel (user decision): *Start over* tunes it and seeks its program to 0:00, moving the schedule like the player's Start over key (`PlayerRoute(restart = true)`). *Watch on demand* opens the on-demand player for a program on now from its start, and *Resume on demand* from where the channel is (once it is a minute in); each line says where it starts and what differs from the channel ("From the start, then the next episodes.", "From 15 min in, then the next episodes."; a movie's say "off the schedule"). *Watch now*, *Resume* and *Play from the start* play on demand too and leave the channel as it is. Future and aired programs share *Watch now*; the airing time stays in the detail, without implying the profile watched it. Positions read as minutes in ("From 12 min in", "Resume from 31 min in"), never as a clock time. Each choice wears one icon wherever it is offered (`WatchIcons`, user decision): *Watch live* the nav bar's Live TV, *Watch on Demand* and the channel player's *On demand* key the nav bar's On Demand, every resume (*Resume on Demand*, *Resume from …*) the update arrow, never the play button, *Start over* the replay arrow, and the rest the play button. Settings rows naming Live TV or On Demand take the same two.
- **Shared playback.** The preview window and the full-screen player show the same `ChannelPlayer`. Each screen acquires it while visible; when the last one releases it, playback stops 1.5 s later unless another screen takes it over, so going full screen and back never retunes.
- **On demand is by channel** (user decision: it fixes choosing, so it is not a library browser). The page is a banner, then one row per guide group in the guide's own order (Settings, Channels, *Groups*; favorites first), each channel a tile: its program's backdrop under the wash with the show's or movie's logo and a ladder of how far the airing has got, then the channel's number and name and what airs: an episode's number in the quiet ink, then its title in bone, as the episode page sets them (a movie's year, then its title under a logo), never joined by a dash. The tile gives no time left, since its ladder shows it (user decision); Continue watching and Next up cards read the same way, and on TV the focused tile's or card's line runs as a marquee. On TV, up and down move a whole row, which lands at the page's top in one move; along a row the focused tile, card or episode stops on the side margin under the row's heading and the row slides under it, as Netflix, Hulu and Jellyfin rows do (user decision: the platform's default holds focus 30% in, which bounced each row and left cards off the heading's edge). Off-air tiles say when the channel is back. What every channel airs comes from one read (`ScheduleDao.airingsAt`), reloaded when the first airing ends and on schedule or library changes. A program over the profile's maturity rating shows as blacked out (see *Profiles, roles and parental controls*).
- **The banner** deals N channels airing something, at random, once per visit (Settings, Channels, *Banner*: 5 to 30, 10 by default, shared like the channels; the deal holds while the page reloads; programs the profile may not watch are never dealt). Each slide is the program's backdrop under the wash with the channel's number and name, the logo, the episode, ON NOW with the time left, two lines of overview and the ladder; squares count the channels. It cuts to the next channel every 8 s while focus is elsewhere and holds while focused; left and right (or a swipe) step it, and left at the first channel goes on to the rail. OK opens the channel. The Movies and Series banners deal only what is still to watch (user decision): a movie or series watched through never shows there, and one part-way through shows its ladder without the time left. Local titles and Recently added appear immediately; server watch marks and Continue watching / Next up arrive independently. Fresh marks are reused for up to 60 s, invalidated when playback reports finish.
- **A channel's page** is about the program it airs now, or the next one while it is off air (*Up next*); it stays on that program even after it ends while the page is open. The hero shows the channel's number and name, the episode's still (a movie's poster) with the airing's ladder and the time left centered under it, the logo, facts, when it airs, and three lines of overview on TV. The picture and its time left are one group, its parts the same gap apart as the group beside it, and the two groups are centered on each other (user decision); a movie's or episode's own page puts its time left under its picture the same way once it is started. Then the watch choices, two to a row from 600 dp: *Watch live*, *Start over*, *Watch on demand* and *Resume on demand* (off air: *Watch live* with when it's back, and *Watch now*). *Add to a channel* isn't a way to watch, so it sits at the page's top end (user decision): at the end of the hero's channel line on TV, in the back bar on phones. Jellyfin's own resume point isn't a choice of its own; an episode's row plays from it. A show lists every episode within the rating limit, by season tab (the on-air season open), each with its still, its length (the time left once started on demand, "12 min left"), a check once watched through, and two lines of overview. On TV, focus on the keys holds the page (and a title's own page) at its top with the whole hero in sight, so moving along them never scrolls; down from them goes to what is right below, the season tabs or the first episode. The episode list is On Demand only (user decision): only the hero says what the channel airs (its *On now* segment, and the ladder and time left under its picture, which always stay), so no row carries a live line and the season tab carries no on-air square; the episode on the channel is ringed as the page's current episode (user decision, replacing the earlier plain row), never in the aired look. OK on an episode plays it from its resume point, or from the start; holding it (or Menu) offers resume, *Play from the start* and Add to channel, and for the episode on the channel the page's own choices. On demand and its channel pages use the guide's margins and gaps (32/12/8 dp on TV, 12/8/6 on phones: `screenSide`, `screenEdge`, `screenGap`), so moving between Live TV and On demand never shifts the edges. Resume points and played marks for the whole show come from the same one request (`Playstate.episodeWatch`, read into `WatchMarks`) when the page opens and again when it comes back into view. An episode counts as watched through only when Jellyfin has it explicitly marked played (whichever app did it), and then reads as aired, for you, the episode on the channel too (DESIGN.md, Watched): its still's foot says WATCHED behind the ticked square (`WatchStrip`), the still lies under the guide's past shade and its title goes quiet, never in the accent. A played episode being watched again shows the square before its new ladder. A season watched through carries the ticked square in place of its count. With the server out of reach, or no watch history kept there, the lists show neither.
- **On-demand playback** has its own player (the channel player stops first, since many TV devices run one video decoder): OK on the picture pauses and brings the banner in with *Play* focused (user decision; Menu or Info bring it in without pausing), left and right jump 10 s back and 30 s ahead, the remote's previous and next keys step through the show. The banner's label always reads ON DEMAND, paused or not (user decision). The banner always shows its keys, tracks on the left and the transport on the right in the remote's order: *Previous*, 10 s, *Pause*, 30 s, *Next*, pause in the middle and focused first. Up, down or Menu moves focus into them; phones get a seek bar. Previous and next follow the show's episode order wherever the episode was started; at either end of the show the key stays in place, dimmed, and focus passes over it, and a movie has neither. Episodes continue into the rest of the show. What it leaves in Jellyfin follows Settings, *On demand* (see *Jellyfin watch history*), and it is kept as an `ON_DEMAND` watch event.
- **Skipping is On Demand only** (user decision: channels play like broadcast TV and skip nothing). The on-demand player reads each item's media segments from Jellyfin (`/MediaSegments/{id}`, 10.10 and later; `SegmentSource`) in the background as the item is resolved, so a slow or old server never holds up playback; a server without segments simply offers nothing. Jellyfin's segment providers fill them in: the Intro Skipper plugin is one, so once it is installed and its segments are made, its intros and credits arrive like any other provider's (its own segment endpoints need an admin, so they are never read). Kinds: intro, outro, recap, preview and commercial; unknown kinds and stretches under a second are dropped. Each kind has a per-profile action (Settings, Playback, *Skipping*; `playback.skip.<kind>.<profile>`), Jellyfin's own three: *Ask to skip* (the default), *Skip* or *Play*. *Ask to skip* shows a Skip key (*Skip Intro*, *Skip Outro*, *Skip Recap*, *Skip Preview*, *Skip Commercial*) for the whole segment except its last second (`playingAt`, unit-tested; user decision: it never goes before the segment ends): in the banner under the tech line while it is up, alone at the bottom end and preselected in rose (touch too) while it is hidden. OK skips while the key stands alone, whatever holds focus, or while it has focus in the banner (it takes focus as it comes on TV). The player decides on key-down, from what plays at that moment, and acts on key-up, so a banner coming or going between the two never turns a skip into a pause; the picture acts on an OK release only when it took the press too. Once the key goes, focus returns to the picture, or to the banner's keys while they are up. *Skip* jumps past a segment the first time it starts while playing; seeking back into it plays it. Skipping seeks to the segment's end, so an outro that runs to the end of the file ends it there: the next episode follows and the view counts as watched through, as in Jellyfin's apps.
- **Add to channel** adds the show (for an episode) or the movie to a channel's *always include* picks and drops it from its excludes; the schedule changes after the airing on now and the next one. It can also create a new channel of its own.
- **JankStats** runs in debug builds and logs, every 5 seconds of drawing, how many frames missed their deadline (`adb logcat -s Anstelle/Jank`).

### Audio and subtitles

- **Player controls.** Both channel and on-demand players show Audio only when at least two supported audio tracks can be selected, and Subtitles only when at least one supported subtitle track can be selected. The subtitle list always includes Off, including when there is only one subtitle track. Selecting a choice (including Off or the current track) returns TV focus to the Audio or Subtitles control that opened the list; touch returns focus to the picture. Both players share this selection behavior in `TrackChoices`. Controls and open track lists refresh as tracks load or the program changes; TV focus returns to an available control when a track control disappears.
- **Defaults per profile** (Settings, *Playback*): an ordered list of audio languages, a subtitle mode (Jellyfin's names, user decision: *Smart*, subtitles when the audio is in a foreign language; *Always*; *None*) and an ordered list of subtitle languages. They are stored as `playback.audio.<profile>`, `playback.subtitles.mode.<profile>` and `playback.subtitles.<profile>`, the lists as ISO 639-2/T codes (`jpn,kor,eng`). Every program, on a channel or on demand, starts on them; a track picked in the player only changes the program on now.
- **Track names** (`TrackLabels`, unit-tested), the same in both players: a track is its language alone. Tracks that share a language add only the facts that tell them apart (English · Signs and English · Full; English · 5.1 and English · stereo), and are numbered when nothing does. The banner's audio and subtitle keys show the language only.
- **Rules** (`TrackRules`, unit-tested). Audio: the first listed language the item has, else its default track. Subtitles: the first listed language the item has, a full track before a forced one, else none. *Smart* shows none when the audio is in one of the subtitle languages; audio without a language counts as foreign. Languages are compared as ISO 639-2/T, so `ja`, `jpn` and `ja-JP` match, and so do `fre` and `fra`.
- **Direct play.** Media3 picks the audio from the language list; `LanguageTrackSelector` (a `DefaultTrackSelector`) picks the subtitle by the rules once the audio is known. Subtitle files next to the video are loaded alongside the stream.
- **Transcoded streams** carry the audio track asked for (`audioStreamIndex`, picked on the device) and no subtitles, so the subtitle the rules pick, if it is text, is loaded next to the stream from `/Videos/{id}/{source}/Subtitles/{index}/Stream.ass` (or `.srt`). The player only offers that one. Image subtitles (PGS, VobSub) aren't available when transcoding.
- **Sync stores the tracks.** Each item keeps its audio and subtitle streams and its font attachments (`media_item.tracks`, JSON), so picking them needs no server call, and its audio languages with the default first (`media_item.audioLanguages`, `|jpn|eng|`), which the catalog reads to tell anime from cartoons.
- **ASS and SSA are drawn by libass** (`io.github.peerless2012:ass-media` 0.5.1, the library Jellyfin's Android TV app uses), so styling, positioning, karaoke and animation look as authored. It draws in its own layer over the video (OpenGL, at most 1080p, scaled up on 4K screens). Fonts come from the Matroska file's attachments or, for a side-loaded subtitle, from the item's attachments (`/Videos/{id}/{source}/Attachments/{index}`, kept in `cache/fonts` up to 100 MB, each font once by its contents since every episode attaches the same fonts under its own URL; tuning waits at most about 3 s for them).
- **A file's own fonts are read once.** Anime files carry 5–33 MB of fonts in their Attachments element, ahead of the first frames, so a direct-play tune read all of it before the track list was known (0.5–3.4 s on the TV AVD), and so did every standby readied on such a channel. The fonts a file hands over are kept in `cache/fonts` under the item's attachment URLs as they are read (written off the loading thread, so a first play reads the file as before). From then on a tune of the same item hands libass every font from the cache before preparing, and the extractor seeks past the Attachments element with a new range request instead of reading it (`FontMatroskaExtractor`). It gets the fonts only all or none: with any missing it reads the file's copies as before. `MatroskaExtractor.read` is final, so the wrapper turns the skip into `RESULT_SEEK` at the reader's next element read; `ProgramTransitionTest` loads a sample with a 512 KiB attachment in 588 KB the first time and 63 KB once it is kept.
- **libass holds one item at a time.** It drops its tracks whenever the player moves to another item, so a program or episode with ASS subtitles isn't queued behind the one before it. Live TV prepares it on the existing standby shortly before the boundary; On Demand starts it separately. libass keeps every font it is given until its player is released, so each font goes in once. ass-media 0.5.1's GL view publishes its render thread before starting it, so a video frame in between failed playback (seen once in 20 warm swaps onto an ASS channel); `SubtitleOverlays` wraps libass' frame callback so such a frame only skips its subtitles.
- **Views.** The full-screen player, the on-demand player and the guide's preview put their player's libass layer into the `PlayerView` (`SubtitleOverlays`). When two views show the same player, the one opened last draws. In the guide's preview the whole subtitle layer (text cues and libass) shrinks toward the picture's top edge until its foot clears the channel strip, so dialogue sits just above the strip instead of behind it.
- **Plain subtitles** (SRT, WebVTT without styling) are white with a black outline and no box in every player (`SubtitleStyle`, user decision), whatever the system's caption style says. A cue's own colors still apply, and ASS keeps its authored look. A setting for it can come later.

### Profiles, roles and parental controls (Phase 8)

- **Profiles are Jellyfin users.** A profile shows its Jellyfin user's name and picture, read again at every library sync; nothing local names it. No profile exists before a server: the app opens on *Add a Jellyfin server*, full screen, and that sign-in's user also becomes the first profile, the owner, with a session of its own (user decision; a password is used twice, a Quick Connect sign-in approves a second code with its own token, `ServerRepository.approvedSession`). *Add a profile* signs in (Quick Connect or password) and makes a profile from that user: on the only server signed in, or, with more than one, on the one picked first from a short list (user decision). A profile has **one Jellyfin user per server** (`profile_account`; user decision): the profile page has a sign-in row for each connected server. Each sign-in uses a device id of its own (`profile-xxxxxxxx`), so it never replaces the server's session or another profile's, and its token sits in the Keystore token store keyed `<server id>/<device>`. The profile is named after its user on the first server it has one on. The library and its sync stay on the server's own sign-in (user decision).
- **Who a profile is on a server** (`ProfileRepository.watchAccount`, user decision): with a user of its own there, the profile **plays as that user** (streams open with that user's token and device, so the server's own access rules apply and Jellyfin's dashboard shows who is watching) and its watched marks and resume points go there. Once that sign-in's token is gone, nothing plays as anyone else: the player asks to check the sign-in. On a server where it has no user of its own, a profile only plays as the server's own sign-in, keeps no watch history there, and its parental rating still applies.
- **Library access** (user decision): channels are shared, but a profile sees only what its own Jellyfin user may. Every library sync lists, ID-only, what each profile's user can see in the synced libraries (`LibrarySyncer.findHidden`: the user's own views, then each one's item ids, so Jellyfin applies the user's folders, parental rating and tags), and the rest is kept for the profile in `profile_hidden_item`. Such a program still airs, blacked out like an age-restricted one but as **No access** (`Restriction.NoAccess`, `ProfileAccess`), joins the restricted stretch around it, never plays on demand and drops out of a show's episode list. A channel whose every upcoming program is hidden from the profile leaves its guide, On demand and surfing altogether (`ProfileRepository.tunable`, `ScheduleDao.hiddenChannels`; user decision: what a profile can't use isn't shown). A new sign-in clears what was hidden from the user before and syncs the server to look again. A library the server's own sign-in can't see never reaches any channel, so that sign-in wants the widest access.
- **Roles** (user decision, `ProfileRights`, unit-tested). The first profile is the **owner**, the root admin; there is exactly one while the app is configured. The owner makes other profiles **admins** and back, edits every profile without its PIN, can't be deleted directly, and can hand the owner role to another profile (*Transfer ownership*, which asks first), staying an admin. Removing the owner's last valid server account instead requires the server-removal transfer or start-over flow above. An admin edits members' profiles without their PINs and the admin's own, never another admin's or the owner's. A **member** edits only the member's own profile. Only the owner and admins add profiles.
- **No access means not shown** (user decision): a profile never sees a setting it can't change. *Manage profiles* lists only the profiles the one watching may edit; on the profile page, *Parental Rating* shows only to the owner or an admin editing a member, *Admin* and *Transfer ownership* only to the owner editing someone else, and the *Permissions* heading only when one of them shows.
- **PINs.** 4 digits, stored as `pbkdf2$20000$salt$hash` (PBKDF2-HMAC-SHA256 written over `Mac`, since `PBKDF2WithHmacSHA256` arrived in API 26). A profile's PIN is asked when switching to it (always at launch) and before editing one's own profile (user decision). Five wrong PINs in a row block PIN checks for 30 seconds.
- **App-wide settings are the owner's and admins'** (user decision): servers, channels (lineups, groups, playback, Add to channel, logos) and web control. A member doesn't see them at all: Settings shows only Playback, Watch history and Theme, the guide and On demand offer no *Add to a channel*, and the empty-guide page has no Settings link. A member who lands on one of those routes anyway (a restored back stack) is sent back (`AdminOnly`). Pairing a browser is app-wide too: on a member's profile the TV shows no PIN and refuses to pair (see *Web server security*).
- **Per profile** (user decision): watch history (*Live TV* and *On demand*, stored as `sync.live.<profile>` and `sync.ondemand.<profile>`), the dashboard (`dashboard.<profile>`), the theme, audio and subtitles, skipping, the guide's open tab and the last channel. Deleting a profile signs its Jellyfin user out and removes its settings.
- **Channels are shared** (user decision): every profile sees every channel, group, number and schedule; channel tables carry no profile. The library's channels are made once from the whole library.
- **Parental Rating** (Permissions on the profile page, user decision): members only, set by the owner or an admin. The choices are Jellyfin's own ratings (user decision): the server's `/Localization/ParentalRatings` table, kept at every sync (`ratings.table.<server>`), one level per score, from *No limit* down. A level shows only when some item in the library scores above the level under it and up to it, so every step changes what plays; items rated in another country's system ("NC16", "12+") count by their score. A level is named with the table's ratings the library carries most, at most two ("TV-MA / R"), else the table's first for that score (`RatingLimits.levels`, unit-tested). Before the first sync stores a table, the library's own ratings stand in. A program rated over the limit, or unrated under a limit, still airs on its channel but is **age restricted** for the profile (`Restriction.Age`): its picture and backdrop are blacked out, its overview is dropped, and its title, logo and episode are blurred wherever they show (user decision; `Modifier.obscured`, a real blur from API 31, a solid bar on older devices such as Fire OS, and screen readers hear "Restricted"). Back-to-back restricted programs count as **one stretch** (user decision): the guide merges them into one cell (`ProgramStrip.mergeRestricted`, unit-tested), and every "until" (the player's, the guide's cell and actions, On demand's tile and channel page) is the end of the whole stretch (`ScheduleDao.restrictedUntil`: the first slot from there that is off air, or within the limit and not hidden from the profile). The channel player keeps the screen dark with a lock, AGE RESTRICTED and UNTIL the stretch's end, then tunes itself again (the program's rating, the profile's limit and where a hidden program comes from are never shown; user decision: a child watching needn't know; the off-air screen takes the same mark, see `DESIGN.md`, Stand-in Mark); a restricted program is never queued behind another or pre-warmed, and nothing is reported. The guide's cells lie on the ground with a lock and AGE RESTRICTED  UNTIL …, and its actions offer only *Watch live* (dark) while the stretch airs. On demand never deals a restricted channel to the banner, its tile shows the lock and AGE RESTRICTED over a black picture and UNTIL … under it, the channel page offers only *Watch live*, nothing over the limit plays on demand (the on-demand player shows the same dark screen), and a show's episode list keeps to the limit.
- **Wording and grouping** (user decision): the profile page never calls a profile "it" or uses a personal pronoun, and repeats no profile name in a row (the page title carries it). It has two groups, the way account pages group settings: *Profile* (Theme; the sign-in, *Authentication* with one server or one row named after each server when there are more, showing the Jellyfin user the profile plays as there, or *Not signed in*; PIN, a switch that sets one or removes it, and Change PIN while one is set), the same for everyone who may edit the profile, then *Permissions* (Admin, Parental Rating, and the Transfer ownership button), what the owner or an admin sets. Row titles are two words at most (user decision). The *Delete profile* button stands apart at the foot under no heading; both it and Transfer ownership ask first.

### Themes (Phase 8)

- **16 built-in themes** in `core/theme/src/main/assets/themes`, Rose first: Amber, Cobalt, Contrast, Ember, Frost, Lagoon, Lilac, Mint, Mono, Moss, Paper (light), Phosphor, Plum, Sepia and Velvet. `tools/themes/generate_themes.py` builds each one from a hue ladder and a signal color in OKLCH and checks contrast floors; `ThemeContrastTest` checks every shipped file. They are copied into the `theme` table at start (`ThemeRepository.seedBuiltIns`).
- **Each profile wears one** (Settings, *Themes*); the whole app re-themes at once, and phones switch their system bar icons for light grounds.
- **The designer** edits a copy (built-in themes never change): the name, each color role as brightness, saturation and hue ladders (OKLCH lightness, chroma and hue underneath) or a hex code, then *Type* (headings, body, text size) and *Screen* (guide rows, progress cuts, scanlines). One theme preview explains everything in place of info notes. Each color and each Type or Screen setting opens its own page beside it (no dialogs), editing a copy: *Done* (at the top beside a red *Discard*, on every device) hands it to the theme, *Discard* or Back drops it; the settings live once in `themeChoices` (`themes/ThemeDesign.kt`), and the web applies a pick through the device. Twelve color roles: on-air guide cells and the player's shades wear `surface`, the banner's text `text`, the now line `accent`. Colors that are hard to read against each other are named in plain words (no contrast ratios), with which one to make brighter or darker, following each edit. Edits are kept only by *Save*; leaving with edits unsaved asks to discard them, and *Use theme* saves first. The web reads readability for unsaved edits from `POST /api/themes/{id}/spec/check`.
- **Scanlines** are a cached 1-pixel-wide bitmap repeated by an `ImageShader` over everything, video included, so a frame allocates nothing (API 25 has no `RuntimeShader`).
- **Import and export:** phones use the system file picker; a device without one (Google TV) points to the web UI's Themes page, which imports and saves theme files (`POST /api/themes`, at most 64 KB; `GET /api/themes/{id}` as a file).
- **TV text fields** open the on-screen keyboard only on OK, so moving through a form no longer pops it up.

### Dashboard (Phase 9)

- **Each profile's own watch stats** (user decision), like a phone's screen time page: every profile, members included, sees only its own; there is no view of other profiles. The old log viewer is gone (logs still reach logcat), and Jellyfin sessions and sync status aren't planned.
- **Capture is a by-product of playback.** Both players hand the reporter their play and pause edges (`onIsPlayingChanged`), one timestamp per change (`PlayClock`), so a view's time is what actually played: pauses and buffering don't count. When the view stops, `DashboardHistory` keeps it if it played 30 s or more and the profile has the dashboard on: one `watch_event` row per local day it played on (a view across local midnight is split there, and a day the clocks change keeps its real length), with the episode or movie type and whether it was watched through (`WatchRules`, on its last day only). Rows are read by `(profileId, localDay)`. No rollup tables, worker or timer; `ScheduleCleanupWorker` drops rows older than 400 days in one indexed delete.
- **Opt-out** (user decision): *Dashboard* on the Watch history page (Settings, Playback) and *Turn off* at the dashboard's foot, per profile, on by default. Turning it off asks each time: *Keep history* (it comes back when the dashboard is on again) or *Delete history*. Off, nothing is kept and the Dashboard tab is gone for that profile.
- **Figures are read only while it is open** (`DashboardStats`): grouped SQL over the profile's `localDay` range on the IO dispatcher, again whenever a view stops (Room's invalidation of `watch_event`), and plain Kotlin over the results for the bars, hours, streaks and sittings (`buildScreenTime`, `StatsMath`, unit-tested). Both reads run in the `Stats` trace section and log their time (`adb logcat -s Anstelle/Stats`).
- **The page is a two-pane console** (user decisions: it leads with what was watched; no title while there is something to show, like Live TV and On Demand; the title shows only on the empty page). Ranks on the ground: tabs in the order Channels, Movies, Series, Genres (Channels open first), the span they cover at the row's end, then the top five: number one large on its backdrop, two to five as ruled lines, each with the time and a ladder of its share (the backdrop is the item watched last, or most for a genre). The meter on coal beside it (under it on phones and screens under 720 dp): Today against the daily average of the 7 days before it (counted from the first day anything was kept) as two ladders on one scale; the Day (24 hourly bars), Week (from the locale's first day), Month or Year (12 monthly bars) chart, each bar split Live TV and On demand, opening on this week, with the span's total and a stepper to the period before or after (never past today); then the habits as readings (daily average on a month or year, peak hour, current and best streak, longest sitting, views, episodes and movies finished) and Turn off. Picking a bar re-deals the ranks for that hour, day or month in a 140 ms cross-fade; left and right on the chart move the pick and run on into the period before or after, OK or a second tap on the bar clears it. The chart's scale ticks every round step, at most eight of them (every 2 hours up to 16), in whole minutes only up to an hour. A view that runs past midnight counts as a view on both days. Genres come from the library while the item is still synced; a channel that no longer exists drops out of the channel ranks but its time still counts. On phones the ranking tabs scroll sideways when they don't fit beside the span.
- **Sittings** are views less than 5 minutes apart, from the first one's start to the end of the last. A streak is the days in a row with anything watched; the current one is still alive through yesterday.

### Settings (Phase 10a)

- **Native to each device** (user decision). On TV, settings take Google TV's guided panel: on the ground at the left the breadcrumb, the page's title, what it does and what it is about (a theme's preview, a server's readout, what a channel airs); on the right a coal panel, edge to edge in height, holding the list. Phones get Android's settings: the title in the back arrow's own row on sub-pages (user decision, as Android's settings do) and in the bar itself on the home, flat rows, and the page's explanation as the closing note with an info mark. Explanations are one short line (user decision: nothing the row or title already says; no rules of thumb, no how-it-works), and live only in that info note (on TV, under the title with the same mark), never inline in the list (user decision): rows show state, and inline lines are kept for problems, status and empty lists. Touch screens 840 dp and wider take the guided panel, with a back arrow over the breadcrumb (`SettingsPage` in `core/theme`).
- **One vocabulary** (user decision): rows are things, buttons are verbs, and what sits at a row's end says what it does. A chevron opens a page (`LinkRow`); a switch turns something on or off, on TV as well (`SwitchRow`); a drop-down mark under the value in use opens the choices as a radio list, each with what it does (`ChoiceRow`); a pencil opens the value for typing (`TextRow`); the overflow mark opens an item's own menu, such as rename or remove (`MenuRow`, and a separate key at the end of a theme's row); a drag handle after it puts a list in order (`ReorderRow`); a radio or checkbox at the start selects (`OptionRow`, `CheckRow`); a fact has nothing at its end and takes no press (`InfoRow`). Verbs (Sync now, Add server, New channel, Add audio language) are buttons, never rows, sharing their line evenly on TV and phone (user decision): one alone spans the list, two split it half and half, and buttons whose labels don't fit their share stack, each across the list (`SettingsButtons`). A destructive verb is a `DangerButton` at the page's foot, apart under no heading, and asks first, naming what goes and what stays. Search fields and the sign-in form stay inline. On phones the page's one primary is rose at rest and bone on focus, the rest coal high. On TV no button is rose at rest (user decision: there rose only ever means focus, so a rose button at rest reads as focused): the primary is coal high like the rest and focus leads to it. Destructive ones are red on both.
- **Danger** (user decision): everything destructive (delete, remove, transfer ownership) wears one fixed red outside the themes, `DangerColor`: destructive buttons filled with it, destructive rows and menu entries with it on their icon and as their focus fill, the answer to a destructive question as the red button.
- **Sheets** open over their page: on TV as Google TV's next panel (the guidance names the setting, the panel holds the radio list, the menu, the field with Save and Cancel, or the question with the answer and Cancel as two buttons side by side, the answer red (user decision: not rows), focus starting on Cancel; Back closes it and focus returns to the row or button that opened it); on phones as Android's dialog, and an item's menu as the overflow menu under its row (`SettingsSheets`).
- **The home is flat** (user decision): one row per area with a short state under it and no headings (Playback names the first audio language, Watch history says On or Off; user decision: no long or repeated lines), the way Android's and Google TV's settings open: Servers, Channels, Playback, Watch history, Themes, Web control and Backup; a member sees Playback, Watch history and Themes. On TV the guidance shows the focused area at a glance (user decision: no paragraphs): Themes its preview; the rest a readout in the server page's language, a hairline frame with headings behind their icons, figures in tabular digits and checks: all servers as one readout of a fixed size however many there are (how their syncing stands, the movies, series and episodes they hold together, how many servers and how many need attention; user decision: a summary of all, never a list); channels on air, custom and library-made, favorites, groups and hidden; the audio and subtitle languages in order with the subtitle mode; Live TV's and On Demand's Status and Progress as checks, and the dashboard; web control's state, address and paired browsers; what a backup holds (Backup, last on the home, owner and admins only).
- **Pages.** *Servers* (renamed from Media servers, user decision): Add server (the page's primary, rose like New channel; user decision), then each server opening its page: the readout, Sync now and Full sync, a switch per library, the Jellyfin user, Remove server. *Live TV* (the settings page, was Channels; user decision): New channel; *Configuration* (the section, was Live TV) with Groups (was Guide with Channel numbers); the On Demand banner's size; then a *Channels* section with Custom and Library, each a row with its count that opens that kind's page, the way On Demand's Rows section opens Movies and Series, so a long custom list never stands between you and the library's channels; each page lists its channels by number with a search by name or number at its top (while it is typed, only what it finds is listed) (user decision). A channel's page: what it airs now and next, Watch, Lineup, Group, Favorite, Visible, then *Playback* with Series and Movies, Name, Logo, Delete channel (no Number: it follows the group and name); a library channel's page has Watch, Favorite and Visible only. Series shows while the lineup airs episodes and Movies while it airs movies (both while it airs nothing yet). Once daily is a switch at the foot of the Movies sheet, under *Repeats* (user decision: on its own row it read as a third playback); it flips without closing the sheet (`SheetSwitch`, whose phone dialog says Done instead of Cancel), the Movies row's summary says it ("Shuffle, once daily"), and it only shows while the lineup can keep to it (series between the movies, or a day of movies). ### Backup and LAN transfer (Phase 10b)

- **One versioned JSON file** (`Backup`: `format` `anstelletv-backup`, `version` 1, enums as their stable codes like the database). It holds what the library can't rebuild: the servers and which of their libraries sync (never a token), the profiles (role, PIN hash, rating limit, theme by built-in key or custom id) with their Jellyfin user on each server, custom themes, groups, every channel with its lineup, seasons, dayparts and logo (the stored file, WebP or PNG, in Base64; a restore makes it standard again on the device it lands on), the settings except the device's own (`web.enabled`, `web.port`, `profile.active`), and the dashboard history of the profiles that keep one. Media items, schedules and what a profile can't see are left out: the sync rebuilds them. A file is named for the app, the device and the day (`anstelletv-<device>-<day>.json`). Another kind of file, one from a newer version, or one whose references don't hold is refused before anything changes (`BackupFormat`, unit-tested).
- **Ids travel**: a restore keeps the backup's ids for servers, profiles, groups, channels and seasons, so settings keyed by a profile or server, the guide's open tab, the last channel and the dashboard keep pointing at the right things. Custom themes get new ids; built-in ones are this app's own, matched by key.
- **Library channels come along** (the plan had the sync rebuild them): they keep their numbers, favorites, hidden state and dashboard history, wait off air for the library, and the library sync takes them over by their key (see *Following the library* for why none is removed meanwhile).
- **History finds its items again.** A view names its item by server and Jellyfin id; restored rows wait in `restored_item` and point at the item once their server's next sync has fetched its libraries (`BackupDao.settleRestoredItems`, run by `LibrarySyncer`). An item no longer synced leaves its row without one (its time still counts), and a view of a channel the backup doesn't have drops out of the channel ranks.
- **A restore replaces everything** after one question saying what comes in ("1 profile, 94 channels and 2 days of history from the file replace what this device holds…"). Built-in themes stay; paired browsers go with the profiles that paired them, so every browser pairs again. Sign-ins never travel (`SignIns`, unit-tested): a server this device is already signed in to stays signed in, as this device's user at this device's address; every other sign-in the device held, a server's or a profile's, is signed out on its server and forgotten; a profile's own sign-in survives only a restore on the device that made the backup. Libraries come back unsynced, so every server fetches in full right after. No sync, channel sync or schedule update runs meanwhile (each has `paused`), the restore runs to its end in the app's scope, and then the app starts over (`RestoreSignal`, a process restart), so nothing from before stays in memory and the launch picker asks who's watching.
- **Who** (decision): Backup is app-wide, so the owner and admins see it; restoring replaces every profile, the owner's too, so only the owner restores or copies a backup in.
- **The page** (Settings, *Backup*): the readout of what a backup holds and when one was last taken (*Saved* and how long ago, also the line under Backup on the home; every export counts, a browser's and another device's copy too), then *Save backup* and *Restore from file* side by side (user decision), then *Nearby devices*: the devices found on the network and *Enter address*. A device without a real file picker (Google TV has only a stub that says no app can) never offers Restore from file, and both point to the web UI's Backup page instead: saving is `GET /api/backup/export` (paired, `no-store`), the same file, and the owner restores from there.
- **Copying from another device.** A device serving web control advertises `_anstelletv._tcp` over DNS-SD on every network it binds to (`NearbyDevices`); the Backup page lists the others while it is open, and an address can be typed where the network blocks multicast (port 8765 by default). Copying pairs like a browser (`PeerTransfer`): the other device shows a PIN (*Pair a device* on its overlay, the web server's notification elsewhere), this one takes it on the PIN pad (six slots in two threes, as the other screen shows them), sends it back and takes the token from the cookie, downloads `/api/backup/export` with `Authorization: Bearer`, then unpairs (`DELETE /api/session`). A wrong PIN asks again for the same pairing.
- **First run**: *Add server*, the screen a new install opens on, also offers *Restore backup*, so a new device takes over an old one's setup instead of starting from a server.
- **What a file gives away**: the PIN hashes (four digits under PBKDF2 are quick to try, so anyone holding the file can learn the PINs), server addresses and user names. Only paired browsers and devices can download one.

The Themes list previews the theme pointed at, else the one worn. The browser tab always says AnstelleTV (user decision). Nothing plays in the browser, and there are no per-profile pages: profiles, playback languages, watch history and the dashboard stay on the TV. ### Performance and resources (Phase 12)

The aim (user decision): the least CPU, memory, network and storage the app can run on, without taking anything away from it.

- **Catalog loading.** Movies and Series load only the open kind; Search requests both. Local titles render before channel matching and server calls. Title metadata is reused across visits until library/access changes, and one cached channel-matching pass serves both kinds. The view model keeps completed tab data across visits and cancels reads while hidden. Successful server history is cached for 60 s and refreshed after a playback report. A rejected or unavailable history read is not cached as an empty result. Reconnecting a profile invalidates history even when its access rules stay the same, so Continue watching, Next up and series episode-count badges return on the open tab.

- **Work only for what is on screen.** On Demand's Channels tab reads its tiles and follows the clock only while it is open; out of view (another tab, a page or the player on top, the app in the background) it reads nothing and reads afresh when it shows again. The Movies and Series tabs and Search read library changes and what was watched (server calls) only while open; what came in meanwhile is read once when they show. The guide reads its windows again after a schedule or library change only while it is on screen, else once when it comes back. Before this, the saved tabs went on reloading behind the player: On Demand every few seconds as airings ended.
- **Schedules.** 8 days ahead, not 30 (see *Schedules follow the channel*): 70% fewer `schedule_slot` rows and that much less work at every regeneration. App start and the twice-daily run only top up the schedules that are due (none yet, marked stale or short: `ScheduleUpdater.updateDue`, one query); every other change already updates its own schedules, so the library is read in full only after a sync, an explicit scheduler revision or a new time zone (`Settings.SchedulesMadeFor`). Repeated startup requests collapse independently; an explicit full request after sync remains queued. A full run reads the library once for the library channels and the schedules both. Schedule and channel work runs on two lowest-priority threads (`AnstelleDispatchers.Background`), so the screen and playback keep the CPU.
- **The guide's range scans** are bounded by the longest slot, which takes reading the whole table; it is kept until `schedule_slot` changes (`LongestSlot`).
- **Playback.** The buffer targets 15–30 s and 64 MB per player (Media3's default target is about 125 MB of heap). Surfing's two standbys drop to one once the viewer rests and are let go while idle; one returns briefly before an ASS program boundary. Standby loading stops at 4 s / 8 MB (see *Player pool*); one media chunk can overshoot those loading thresholds. Media3's experimental dynamic scheduling was tried and dropped: with libass on it woke the playback loop more, not less (676–685 against 591–608 CPU ticks a minute on the AVD).
- **Images.** Coil keeps at most 12% of the heap (its default is a quarter) and 64 MB on disk in its own folder (its default grows to 2% of the disk, up to 250 MB; the AVD had 138 MB).
- **Startup.** The built-in themes are copied into the database only after an install or update (`Settings.ThemesSeeded`), and never before the first frame. The web pairing gate reads profiles only once web control serves a request.
- **Housekeeping** (`ScheduleCleanupWorker`, daily): old slots, guide entries and dashboard history go, the font cache is trimmed, and once a quarter of the database file is free pages it is rewritten without them (`VACUUM`): SQLite reuses freed pages but never shrinks the file.
- **The APK.** Release builds come as one APK per ABI (`app-armeabi-v7a-release.apk` for Fire TV, whose system is 32-bit; arm64, x86_64) plus a universal one; debug builds stay one APK. 32-bit x86 isn't shipped. Resources are English only (`localeFilters`): the libraries' translations of their own strings would only mix languages. The Jellyfin SDK's own R8 rules keep every API model whole (about 21,000 methods); they are ignored (`optimization.keepRules.ignoreFrom`) and kotlinx.serialization's rules keep what the app reads. The universal APK went from 28.4 MB to 21.5 MB and the Fire TV one is 9.7 MB; the code from 11.1 MB of dex (61,852 methods) to 8.3 MB (42,529).
- **Measuring.** Macrobenchmarks (`:benchmark`): cold start, guide scroll (`FrameTimingMetric`), surfing (`TraceSectionMetric("Tune")`, the change to its first frame) and the dashboard's first open (`"Stats"`, both reads, logged at info so release builds report it). They run on the device's own library and server: frames need a real stream, so there is no fixture seeder. The benchmark and baseline-profile builds are signed with the debug key, so they install over a debug install without losing its sign-ins. The baseline profile (`:app:generateBaselineProfile`) covers start, the guide, tuning and surfing, On Demand and the dashboard.

### Shared progress and watch shelves (2026-10-15)

- Next up excludes every series already in Continue watching, including when Jellyfin returns a different episode for that series. The repository owns this filter; the catalog reuses its already-loaded Continue watching cards.
- Unstarted episodes show neither a progress strip nor time left. Watched markers remain independent of resume progress. Catalog movie posters retain their existing visibility and no time-left label; title-screen movie posters show the shared time-left label centered below their progress bar. `MediaProgress`, `WatchStrip`, `WatchProgress` and `SegmentLadder` own duration math, artwork presentation, progress rows and segment drawing respectively.
- Both players, on-demand channel lines, movies and episodes repeat the same block width and fixed 3 dp gap. Themes set *Progress cuts* (the designers' *Screen* group): 4 to 64 cuts per fixed 320 dp reference length, default 20. Higher frequency makes thinner blocks across every bar; longer bars contain more of those identical blocks. Whole blocks are centered without stretching or clipping the last block. Older themes acquire the default without a migration.

- TV detail pages open on the primary watch action. Down passes through the selected season tab, then enters the leftmost fully visible episode; Up reverses it. Rail scroll survives page scroll and watch-data refreshes; closing an episode's action dialog restores its card. Continue watching and Next up episode cards open the episode page.
- Title and episode pages carry a square watched toggle in their action row (channel pages don't; they keep Resume on demand beside Watch live when the airing has a resumable point). A series toggle covers every accessible episode; a movie or episode toggle its item. It writes the profile's own Jellyfin history, clears resume points when marking watched, shows Saving while the write runs (TV focus stays), and refreshes catalog history. Unavailable history disables it; a failure shows under the hero; a stale read never overwrites a confirmed edit.
- Channel, title and episode detail pages share `ProgrammeSheet` for the title, episode line, description, errors and restriction mark. The right readout anchors to the picture's bottom with equal shared margins; descriptions have no extra horizontal inset and use the space left after identity, facts and actions. On TV and wide layouts the readout is as wide as a full row of five watch keys plus its margins (`watchKeysWidth`), which scale with the font, so channel pages keep every key and label. Keys are equal rectangles on five slots, 8 dp apart and flush left; fewer keys keep the five-slot width.
